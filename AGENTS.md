TypeScript principles
- No any types unless absolutely necessary.
- Check node_modules for external API type definitions instead of guessing.
- Prefer SDK-provided types, schemas, helpers, and model metadata over local redefinitions. For things like Cline SDK reasoning settings, use the SDK's source of truth whenever possible instead of recreating unions, support checks, or shapes in Kanban.
- NEVER use inline imports. No await import("./foo.js"), no import("pkg").Type in type positions, and no dynamic imports for types. Always use standard top-level imports.
- NEVER remove or downgrade code to fix type errors from outdated dependencies. Upgrade the dependency instead.

Code quality
- Write production-quality code, not prototypes
- Break components into small, single-responsibility files. 
- Extract shared logic into hooks and utilities. 
- Prioritize maintainability and clean architecture over speed. 
- Follow DRY principles and maintain clean architecture with clear separation of concerns.
- In `web-ui`, prefer `react-use` hooks (via `@/kanban/utils/react-use`) whenever possible
- Before adding custom utility code, evaluate whether a well-maintained third-party package can reduce complexity and long-term maintenance cost.

Architecture opinions
- Avoid thin shell wrappers that only forward props or relocate JSX for a single call site.
- Prefer extracting domain logic (state, effects, async orchestration) over presentation-only pass-through layers.
- Do not optimize for line count alone. Optimize for codebase navigability and clarity.

web-ui Stack
- Kanban web-ui uses Tailwind CSS v4 for styling, Radix UI for accessible headless primitives, and Lucide React for icons.
- Custom UI primitives live in `src/components/ui/` (button, dialog, tooltip, kbd, spinner, cn utility).
- Toast notifications use `sonner`. Import `{ toast }` from `"sonner"` or use `showAppToast` from `@/components/app-toaster`.

Styling mental model
- Use Tailwind utility classes as the primary styling system. Prefer `className` over inline `style={{}}`.
- Prefer Tailwind classes over adding custom CSS in `globals.css` when possible. Conditional Tailwind classes via `cn()` are better than CSS overrides for state-driven styling (e.g. selected/active variants). Reserve `globals.css` for things Tailwind can't express: complex selectors (sibling combinators, attribute selectors), app-level layout glue, or styles that genuinely need to cascade.
- Only use inline `style={{}}` for truly dynamic values (colors from props/variables, computed positions from drag-and-drop, runtime-dependent dimensions).
- The design system tokens are defined in `globals.css` inside `@theme { ... }`. Use Tailwind utilities that reference them: `bg-surface-0`, `text-text-primary`, `border-border`, etc.

Testing on Windows
- Sandboxing `HOME` alone is NOT a home sandbox. `os.homedir()` reads `HOME` on POSIX but `USERPROFILE` on Windows, and `getKanbanStorageDir()` prefers `KANBAN_STORAGE_DIR` and then a pointer file at `~/.cline/kanban-storage-dir`. A HOME-only sandbox therefore resolves to the developer's *real* configured storage dir on Windows — which for the hook-script writers and `resetAllState` means creating and deleting files in live user config (this was observed deleting from a Google Drive shared drive). Always use `createTempHome()` from `test/utilities/temp-home.ts`; it pins all three.
- `process.exit()` in the CLI aborts the process on Windows. It tears the event loop down while libuv threadpool work is still in flight (the workspace-state file lock issues fs calls to the very end), and the completing worker then signals a closing async handle: `Assertion failed: !(handle->flags & UV_HANDLE_CLOSING), file src\win\async.c`. The command prints its correct output and *then* dies with exit code 3221226505 (`0xC0000409`). `src/cli.ts` uses `exitWhenIdle()` — set `process.exitCode`, let the loop drain, keep only an unref'd force-exit as a hang guard. Reproduces on the built bundle too, so it is not a tsx artifact.
- Integration tests boot the runtime from source through tsx, which recompiles the entry graph in every spawned process: ~10s per spawn on Windows even warm, versus well under a second on Linux CI. Timeouts live in `test/utilities/integration-timeouts.ts` — a flat 10s start bound raced this and failed with *empty* stdout and stderr, which reads like a silent crash rather than a slow boot.
- Git for Windows defaults `core.autocrlf` to true, so any test asserting byte-exact file contents after a checkout/patch round-trip must pin `core.autocrlf false` on the test repo.
- Test assertions must not hardcode POSIX spellings the code derives per platform: shell quoting (`quoteShellArg` uses `'` on POSIX, `"` on Windows), resolved paths (`resolve("/tmp/x")` becomes `C:\tmp\x`), and PATH probing (`shouldUseWindowsCmdLaunch` scans the *real* PATH, so pin `PATH`/`PATHEXT` in the launch env or a locally installed binary changes the outcome).

Misc. tribal knowledge
- `[vite] ws proxy error: Error: read ECONNRESET` means the runtime sent a TCP **RST**, not that the network failed. The web UI reaches the runtime through Vite's `/api` proxy (`ws: true`), so any `socket.destroy()` or `ws.terminate()` on the runtime side surfaces there as a bare reset with no HTTP status and no runtime log — undiagnosable from all three sides. Read `.plan/docs/prod-runtime-connection-errors.md` before touching this. Two things to know up front: every WebSocket upgrade runs the Host/Origin gate **twice** (the runtime-state hub and the terminal bridge each register an `upgrade` listener), and Vite's `changeOrigin: true` rewrites only the **Host** header — the WS `Origin` header reaches the runtime unchanged unless `rewriteWsOrigin: true` is set, so the runtime's CORS gate sees the *Vite* origin and only accepts it via a `NODE_ENV=development` + `KANBAN_WEB_UI_PORT` escape hatch. Reject an upgrade with `endUpgradeSocket()` (flush the status line, then FIN), never a raw `socket.destroy()`; and always attach an `'error'` listener to a raw upgrade socket, because Node attaches none and an unhandled one crashes the runtime.
- A `proper-lockfile` lock is a **directory**, not a file: it is acquired with `mkdir` and released with `rmdir`, and `proper-lockfile` retries neither. That makes it a poor fit for a synced volume, and Kanban's storage dir is frequently one (`G:Shared drives...`). Three distinct failures come out of this, and they need different fixes — do not assume one covers the others. **(1) Release fails.** `src/fs/lockfile-fs.ts` routes `rmdir` through `node:fs` `rm` with `maxRetries`, but `rm`'s own loop covers only EBUSY/EMFILE/ENFILE/ENOTEMPTY/EPERM — Google Drive actually fails with `EINVAL: invalid argument, lstat '<file>.lock'` from the lstat inside `rm`'s recursive walk, which that loop does **not** retry, so a second explicit backoff over EINVAL/EACCES wraps it. Keep the adapter a module-level singleton; `proper-lockfile`'s mtime-precision probe caches on object identity. **(2) Acquire stalls for ~10s.** Drive keeps reporting EEXIST from `mkdir` on an already-removed lock directory for seconds, and intermittently fails `stat` with EINVAL, so acquirers burn their retry budget waiting for its metadata view to converge. Measured with 4 concurrent writers on one file: 978 mkdir calls per 100 acquisitions (878 EEXIST) versus 183 locally, acquire max 21.5s versus 1.3s. **No amount of retrying fixes this** — the lock has to live elsewhere, so `src/fs/lock-location.ts` puts every lock in a local dir (`tmpdir()/kanban-locks`, override `KANBAN_LOCK_DIR`) named by a hash of the target path. Contended p95 went 10,368ms → 427ms. The trade-off is that a machine-local lock no longer excludes a *different machine* writing the same shared file; that exclusion was already illusory given the EEXIST staleness. **(3) The data write itself.** The lock guards against other writers, not against the sync agent holding a handle, so every mutation in `writeTextFileAtomic` (and `removePath`, which passed no `maxRetries` at all) goes through `retryTransientFs` in `src/fs/transient-fs.ts`. Keep the temp file in the destination directory — moving it to the OS temp dir makes the rename cross-volume and fail with EXDEV.
- You cannot expose the runtime on a public address by binding it there. `getAllowedHostHeaders()` (`src/server/middleware.ts`) accepts only `localhost:PORT`, `127.0.0.1:PORT`, and the bound address, and there is **no env var to extend that list** — so `http://<public-ip>:PORT` returns a flat `403 Host not allowed.` that looks like the app is down. Binding the public IP is not the fix either: on OCI the public address is NAT'd by the internet gateway and absent from the instance NIC, so `bind()` fails with `EADDRNOTAVAIL`; and binding `0.0.0.0` makes `isKanbanRemoteHost()` true, which arms the interactive passcode gate while *still* rejecting the public Host header. The deploy therefore runs the app on loopback behind `scripts/deploy/kanban-host-proxy.mjs`, which owns the public port and rewrites Host/Origin to the loopback authority. Read `docs/deployment.md` before touching any of this. Two traps: the proxy must handle WebSocket upgrades (the same gate runs on every upgrade), and under enforcing SELinux a plain node service is denied the loopback `connect()` with EACCES — which surfaces as a 502 from a proxy whose backend is perfectly healthy.
- Kanban's native Cline agent is powered by the installed `@clinebot/core` and `@clinebot/llms` packages plus the local `src/cline-sdk/` boundary layer, so when Cline behavior is unclear, inspect those packages and `src/cline-sdk/` for the real implementation details.
- Kanban is launched from the user's shell and inherits its environment. For agent detection and task-agent startup, prefer direct PATH checks and direct process launches over spawning an interactive shell. Avoid `zsh -i`, shell fallback command discovery, or "launch shell then type command into it" on hot paths. On setups with heavy shell init like `conda` or `nvm`, doing that per task can freeze the runtime and even make new Terminal.app windows feel hung when several tasks start at once. It's fine to use an actual interactive shell for explicit shell terminals, not for normal agent session work.
- If CI hangs on Node 22 after tests seem to finish, suspect a live subprocess or SDK-host startup path before assuming a slow test body. Read `.plan/docs/node22-ci-hanging-tests-investigation.md` before repeating that investigation. `test/runtime/cline-sdk/cline-task-session-service.test.ts` was the big prior culprit because a unit-style suite was still booting the real Cline SDK host.
- When Kanban runs on a headless remote Linux instance (for example over SSH+tunnel), native folder picker commands may be unavailable (`zenity`/`kdialog`). Treat this as a normal remote-runtime limitation and use manual path entry fallback instead of requiring desktop packages.
- Custom OpenAI-compatible providers (e.g. Modrev models) can't be launched by their own provider id. The SDK session runtime builds its gateway with only the built-in provider registrations and then merely *configures* them (`createGateway({ providerConfigs })` → `configureProvider`, which can't register a new provider); a non-built-in provider id therefore fails `resolveModel`/`getManifest` as "Unknown or disabled provider" and the chat shows "Model stream failed". Note this is a different registry from the `@clinebot/llms` model registry (`hasProvider`/`registerProvider`) that `ensureCustomProvidersLoaded` populates — loading a custom provider there does NOT make the gateway see it. The fix is in `cline-session-runtime.ts`: route non-built-in providers (detected via `isBuiltInSdkProviderId` → SDK `Llms.isBuiltInProviderId`) through a built-in generic OpenAI-compatible proxy provider, passing the model's own base URL / API key / model id so the gateway configures that built-in against the custom endpoint.
- Native-agent (Cline/Modrev) model-response failures do NOT reliably surface as a thrown error from `sessionHost.send`; most arrive as terminal SDK *error events* (`agentEvent.type === "error"` / `run-failed`) that the event adapter turns into a `warningMessage`, and some come back as the send *result text* itself. So a retry built only around a `.catch()` on the dispatch promise never fires for real model failures. The retry in `cline-task-session-service.ts` latches event-driven failures via the adapter's `onTurnError` callback and also catches thrown errors, then re-dispatches; it's parameterized by the `llmRetry*` runtime-config keys (exposed in the API as the nested `llmRetry` object). Credit-exhaustion and user cancellation are never retried.
- The generic provider you route custom models through MUST speak the OpenAI *chat-completions* API, not the Responses API. `litellm` and `openai-native` are Responses-based: they serialize prior assistant turns as Responses `input` items, and a plain chat-completions endpoint (e.g. NVIDIA `integrate.api.nvidia.com`) rejects them with `data did not match any variant of untagged enum InputParam` the moment the conversation contains an assistant message — i.e. every turn after the first. Single-turn works, multi-turn breaks. Route through `openrouter` instead (chat-completions, respects a custom `baseUrl`, preserves multi-turn history). This shows up only in a real conversation; a one-shot smoke test won't catch it, so always test at least two turns.
- Whether a task renders/saves a Kanban-style chat vs. a raw CLI terminal is decided by ONE predicate, `isNativeClineRuntimeAgent(agentId)` (`src/core/agent-catalog.ts`), mirrored on the backend routing fork (`runtime-api.ts startTaskSession`: `useClinePath`) and the frontend panel fork (`card-detail-view.tsx`: `showClineAgentChatPanel`). Native agents (`cline`, `modrev`, `claude`) run in-process through the Cline SDK host and persist a structured conversation; everything else (`codex`, `droid`, `kiro`, …) is spawned in a PTY with only scrollback. So "native" here means "runs through the Cline SDK runtime," NOT "is Cline" — `modrev` and `claude` are native but not Cline.
- `claude` is a native agent (no `binary`), NOT an external Claude Code CLI launch. It runs the Cline SDK pinned to the built-in `claude-code` provider, which authenticates with the machine's **Claude Pro/Max subscription** (via `ai-sdk-provider-claude-code` → `@anthropic-ai/claude-agent-sdk`) instead of an Anthropic API key — there is no secret to store, only a model. The pin is applied in `resolveNativeAgentLaunchOverrides` (`runtime-api.ts`) as `providerIdOverride: "claude-code"` (constant `CLAUDE_NATIVE_PROVIDER_ID`); because `resolveLaunchConfig` silently falls back to the *selected* provider when the override slot is unconfigured, `startTaskSession` guards against launching "Claude" on the wrong model by erroring when the resolved provider isn't `claude-code`. The frontend considers Claude "set up" once its `claude-code` slot is selected (`isClaudeSubscriptionConfigured`, model saved) — no API-key check — because the subscription auth is ambient (the user runs `claude login`). `claude-code` is a built-in SDK provider (`Llms.isBuiltInProviderId`), so the session runtime configures it directly rather than through the generic OpenAI-compatible proxy. Tests that need a still-terminal agent must use `codex`/`droid`, not `claude`.
- For the native `claude` agent, **Claude Code's built-in tools ARE the file toolset** — Cline's tools never reach it, and removing the built-ins leaves the agent with nothing. `ai-sdk-provider-claude-code` forwards only `settings.tools` (the built-in selector) and `settings.mcpServers` into the Agent SDK; it never converts AI-SDK request-level tool definitions into Agent SDK tools. So a `claude` session's real toolset is Claude Code's built-ins plus MCP servers reachable from **Claude Code's own** configuration — never Kanban's. Verified end to end: setting `tools: []` produced a session whose entire toolset was the user's claude.ai account connectors (Gmail/Calendar/Drive, inherited via subscription auth), zero tool calls, task not done. **`Unknown tool: Read` / `Unknown tool: Grep` are not the bug, and they are not harmless either.** They are Cline's agent runtime (`@clinebot/agents` `executePreparedTool`) rejecting tool calls it does not own, while Claude Code executes those same calls internally and gets real results. Two tool loops run against one conversation, so the model is handed `{"error":"Unknown tool: X"}` for calls that actually succeeded. Observed consequence: a session called an MCP tool, reported the correct result, then **retracted it on the next turn and accused itself of fabricating the output** — "That was invented output, not a real observation" — because the injected errors looked like proof the call had failed. The retracted answer contained a millisecond-precision timestamp that matched the real store, so it was demonstrably genuine. Budget for wasted turns, duplicated calls, and abandoned-but-correct work; do not dismiss these lines as cosmetic. The real blockers are the two that actually stop work: Claude Code's interactive permission gate on writes (`Tool call Edit was rejected before execution: Claude requested permissions to write to <path>, but you haven't granted it yet.` — emitted by the bundled `claude.exe` inside `@anthropic-ai/claude-agent-sdk`, so grepping `src/` for it finds nothing), and a `cwd` that is never passed, so the built-ins default to `process.cwd()` and address the **main checkout** instead of the task worktree. Diagnose from the persisted transcript at `~/.cline/data/sessions/<taskid>-<ts>-<id>/*.messages.json`, not from the UI.
- **The permission gate is solvable today; the `cwd` is not.** Claude Code reads `permissions.allow` from `~/.claude/settings.json`, and the process Kanban spawns honours it — verified A/B on one tool, same server, `allow` entry the only variable: 4 `"you haven't granted it yet"` denials without it, 0 and a real result with it. The spawned process also inherits **user-scope MCP servers** from `~/.claude.json` (`claude mcp add --scope user`); proven by process tree, where the MCP server is a child of `claude.exe` whose grandparent is the Kanban runtime. So both routes bypass `@clinebot/core` entirely. **Do not reach for either on its own.** Neither can set `cwd`, so the built-ins still resolve relative paths against `process.cwd()` — the main checkout — instead of the task worktree. Pre-approving `Edit`/`Write` without fixing `cwd` converts a blocked agent into one that edits the wrong tree unprompted, which is strictly worse. Kanban's own MCP settings (`cline_mcp_settings.json` → `createToolBundle` → `extraTools`) do **not** reach `claude`: they ride the Cline tool path, and the provider's `doGenerate`/`doStream` never read `options.tools`. Per-task MCP config is mechanically easy there (one caller, per-task bundle lifecycle, stdio registrations carry `cwd`/`args`/`env`) but only benefits `cline`/`modrev`.
- A complete fix still needs `permissionMode` **and** `cwd` to reach the provider, which **cannot be done from this repo**. The supported route is `CoreSessionConfig.providerConfig.claudeCode`, which `@clinebot/llms` would hand to the provider as `GatewayProviderConfig.options` → `createClaudeCode(config.options ?? {})`; note the nesting, since that parameter is `{ defaultSettings?: ClaudeCodeSettings }` and **not** a bare settings object, so the payload is `claudeCode: { defaultSettings: { permissionMode: "bypassPermissions", cwd } }`. It is dead regardless: the agent-model factory in `@clinebot/core` builds its gateway from a **fresh allowlisted object** — `createGateway({ providerConfigs: [{ providerId, apiKey, baseUrl, headers, models }] })` — so `options` and every vendor sub-object is silently dropped. Setting it typechecks, ships in the bundle, and changes nothing at runtime. `BUILTIN_PROVIDER_REGISTRATIONS` would work but is unreachable (`@clinebot/llms` publishes no deep subpath exports), and `Llms.registerHandler` / `LlmsSdk.registerBuiltinProvider` belong to the older *handler* system, which this path never touches. A local `overrides` shim over `ai-sdk-provider-claude-code` can reach the provider but **cannot** carry `cwd`, which is per-session — so it can only choose between safe-and-useless (`tools: []`) and working-but-writing-to-the-wrong-checkout (`permissionMode` with no `cwd`). Don't ship one. The fix belongs upstream in `@clinebot/core`.
- If you ever do wire an `overrides` shim for something else, two npm traps: a `file:` spec in `overrides` resolves relative to the **dependent** package, not the project root, so the obvious form installs a dangling symlink and silently removes the real package and its subtree (neither `$name` syntax nor a `../../../` escape fixes it; a `workspaces` entry does). And `npm install` then writes a lockfile entry with that same wrong path, which `npm ci` rejects (`Missing: <pkg> from lock file`) — both launchers run `npm ci`. Only a lockfile generated after `rm package-lock.json` records the correct root-relative path, so port those entries onto the existing lockfile rather than regenerating it, which otherwise re-resolves ~558 versions. Unrelated but adjacent: `package-lock.json` is CRLF, `AGENTS.md` is LF, and `package.json` is CRLF except two lines — editing any of them through a text-mode rewrite produces a five-figure phantom diff.
